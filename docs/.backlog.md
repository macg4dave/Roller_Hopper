# Backlog

Blank by design. The [roadmap](roadmap.md) owns milestones, permanent task IDs, dependencies
and completion checks. This file is for detailed task cards and work captured later; it does
not duplicate the roadmap's task list. There are no active cards or newly allocated IDs here.

## Working rules

1. For an existing roadmap task, reuse its `BE-` ID exactly. Add a link to its milestone and
   copy only enough context to make the card actionable; do not create a second task ID.
2. For new work, allocate the next unused ID from the [roadmap ID register](roadmap.md#ids-status-and-maintenance)
   and advance that register in the same edit. Add the task to the appropriate milestone,
   with dependencies and a completion check. Allocate a new `M-` ID if a milestone is needed.
   Never renumber/reuse IDs; execution order comes from dependencies, not the number.
3. Capture an unapproved idea as Planned, marked **proposed scope**. It becomes Ready only
   after scope approval, roadmap placement, completed dependencies and resolved blockers.
   Current roadmap requirements remain in force until an approved change updates them.
4. Keep task status consistent with the roadmap. Use Planned, Ready, Active, Blocked, Done
   or Cancelled. A blocked card names task/blocker IDs and the exact evidence/decision needed.
   Allocate new shared blockers in the roadmap's `BLK-` register; do not create a parallel list.
5. A cancelled dependency does not unblock another task. Update that dependency explicitly.
   If splitting a task, retain its ID for remaining scope and allocate linked IDs for new parts.
6. Mark Done only after acceptance checks, the required ordered gate and the relevant
   authorised evidence pass. Store brief outcomes/links here rather than copying logs.
   Cancelled cards retain their ID and reason. Empty fields may use `Not assigned` or
   `Not yet recorded`; never invent an owner, estimate, due date or pass result.
7. Keep credentials and private network captures out of these cards. Planning a scan is not
   execution authorisation. Follow [AGENTS.md](AGENTS.md) and the milestone's approval gates.

## Task card template

Copy the following into **Task cards** and replace every placeholder. The template itself
does not allocate an ID. Optional priority values: P0 (blocks a required milestone), P1
(required work), P2 (approved improvement). Priority never overrides dependency or approval.

```markdown
### <BE-ID>: <short action and outcome>

Milestone: [<M-ID>: <name>](roadmap.md#<milestone-anchor>)
Roadmap task: <same BE-ID; roadmap acceptance check is authoritative>
Status: Planned
Priority: <P0 / P1 / P2>
Owner: Not assigned
Depends on: <BE-IDs, or no task dependencies>
Blocked by: <BE-/BLK-IDs and exact reason, or no known blocker>
Required decision / evidence: <what closes the blocker, if any>
Scope approval: <agreed requirement or pending approval; include the reference>

Outcome: <user-visible behaviour or concrete decision this task delivers>

Scope:

- <included work and existing functionality to reuse>

Acceptance:

- [ ] <observable result and input/scenario>
- [ ] <failure/race/manual-data preservation case relevant to this task>
- [ ] Required ordered gate passes; evidence matches the task's actual scope.

Implementation notes: <relevant paths/contracts; do not preselect speculative abstractions>

Validation / evidence:

- Revision and environment: Not yet recorded
- Source gate: Not yet recorded
- Deterministic / file / GUI / live-network / AI / platform evidence: <relevant categories only>
- Limits or unverified claims: <what this evidence does not establish>

Completion / cancellation: <outcome and date when completed, or reason when cancelled>
Follow-up IDs: <new BE-IDs if required; allocate them in the roadmap first>
```
